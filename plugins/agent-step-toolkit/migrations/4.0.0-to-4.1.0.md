# Migrate agent-step 4.0.0 → 4.1.0

> Severity: **additive** — nothing is removed or renamed, and a 4.0.0 project compiles unchanged.
> The transforms below are CHECKS: several engine sentences were reworded and a few result entries
> gained fields, so goldens, quoted text and whole-entry assertions may need updating.
> Applied by `/pull-library`; readable standalone.

## What changed

### 1. Required tool calling (opt-in — not applied by this migration)

`AgentStepConfig.tool` gains `toolChoice?: "auto" | "required"`. The default, `"auto"`, is the
behaviour every 4.0.0 project already has: the model answers with text or calls the tool.

Under `"required"` every model turn is exactly one call to the agent-step tool:

```jsonc
// auto — a speaking turn is assistant text, no tool call
"Could you tell me the last four digits?"

// required — speech is a control, and every call classifies the caller's turn
{ "turn": "service", "steps": [{ "action": "respond_to_caller", "params": { "text": "Could you tell me the last four digits?" } }] }
```

- **`respond_to_caller`** is a library control (reserved in this mode, sole-step). Its `text` may
  carry the placeholders `{read_back}`, `{ask_text}` and `{reply_text}`; the engine replaces them
  with the fixed bytes of the caller turn's latest result and refuses a reply that leaves those
  bytes out or rewords them. At a pending `repeatReadBack` confirmation a fresh reply names a kind:
  `{ kind: "clarification", explanation }` (the engine appends the stored read-back) or
  `{ kind: "choice", text }`.
- **`turn: "service" | "misuse"`** rides every call. A turn marked `misuse` on the first call of a
  caller turn is recorded as a `malicious_intent` note in place of its steps.
- **A result's `continuation`** bounds the next call of the same caller turn: `"await_caller"` →
  only the speech step; `{ action }` → only that action.
- The protocol fragment (`composeProtocolPrompt`) composes different text in this mode.

The mode needs host wiring — a hand-rolled agent node using `completedReply`,
`modelToolsForTurn`, `modelToolOptions` and `toolOnlyMessage` — and cannot run on a
`createReactAgent` graph. See "Adopting required tool calling" below.

### 2. Verdict rows can say what happens next (optional, both modes)

```ts
// 4.0.0 — `ok` is the only lever: to stop the batch for a question, the row had to FAIL
located: { ok: false, summary: "Is this the account you mean?", body: { verdict: "located" } },

// 4.1.0 — the outcome stays honest; the boundary is declared
located: {
  ok: true,
  summary: "Is this the account you mean?",
  continuation: "await_caller",     // stop the batch here, wait for the caller's answer
  presentation: "verbatim",         // the summary must be spoken exactly (rides again as `reply_text`)
},
```

| `continuation` | Effect |
|---|---|
| omitted | unchanged: `ok: true` lets the batch run on, `ok: false` stops it and sets `failed_at` |
| `"await_caller"` | the batch stops; the step keeps its `ok` (no `failed_at` when `ok` is true) |
| `{ action }` | the batch stops; the next call must be that action (enforced in required mode) |
| `"continue"` | the batch runs on although `ok` is false; no `failed_at` |

A row with an `ask` may only declare `"await_caller"`; a `backendFailure` row, or one carrying a
`request_handoff` effect, declares none.

### 3. A capture bounce can carry domain guidance (optional, both modes)

```ts
// action.ts
verdicts: {
  // …
  bad_length: { ok: false, summary: "A tax number has nine digits." },
},
invalidParamsVerdict: "bad_length",
```

When a call's params fail the schema parse, the `invalid_params` result also carries that row's
`summary` and body, and the engine instruction tells the model to relay it before asking again. The
row must be a plain failure row (no `stateUpdate`, `effects`, `ask` or `backendFailure`).

### 4. `note_refusal` can speak its decline (both modes)

The control takes an optional `reply`. For a `declined_or_cannot` / `unsupported_question` turn
handled in place, a call that carries it is recorded AND answered in one step:

```jsonc
// 4.1.0 without `reply` (4.0.0 returned the same entry minus `continuation`)
{ "action": "note_refusal", "ok": false, "refusal_noted": true, "kind": "unsupported_question",
  "instruction": "Decline this unsupported question…", "continuation": "await_caller" }

// 4.1.0 with `reply`
{ "action": "note_refusal", "ok": false, "refusal_noted": true, "kind": "unsupported_question",
  "summary": "I can't help with that here. Could you tell me the last four digits?", "turn_complete": true }
```

Nothing needs configuring: the model may start sending `reply` because the control's description
now offers it.

### 5. Behaviour that moves for EVERY project, auto mode included

**Reworded engine text** (model-facing bytes — goldens move). Verified by building one auto-mode
tool against both library versions and diffing every model-facing byte: the protocol fragment and
every domain action's schema variant are identical; exactly the entries below differ.

| Where | 4.0.0 | 4.1.0 |
|---|---|---|
| generic `reply_contract` (`confirm_reply_contract`) | "…Anything else is not an answer: make no call and re-ask the read-back question." | a question about what is being confirmed, and unclear, unrelated or third-party speech, are each answered with one short spoken yes/no question |
| confirmation lockdown refusal (`lockdown_confirmation`) | `A "{action}" is pending confirmation; only the same action with matching params or "{abort_action}" is allowed until it resolves.` | the same sentence, plus: `To act on a different item or value the caller just gave, send "{abort_action}" followed by that action in the SAME call — never repeat the pending question about the item they moved away from.` |
| capture bounce (`invalid_params`) | "…Tell the caller it did not come through and ask them to say it again…" | relay the validation guidance in the result's summary, then ask again; without a summary, say it did not come through |
| unsupported-question decline (`decline_unsupported`) | "Make NO handoff and answer NONE of the question's content…" | decline in one short sentence; the instruction is scoped to this caller turn, and a repeated or rephrased unsupported question is a fresh refusal |
| `ask_contract` supply clause | `When their reply supplies it, call "{action}" with it in "{param}"; if they instead decline, pivot, or ask something else, handle that per your instructions — the ask keeps standing until answered.` | `When their latest reply supplies all or part of this value, call "{action}" with that supplied content in "{param}"; the action validates it. If they supply no new value and instead pause, decline, pivot, or ask something else, handle that per your instructions — the ask keeps standing until answered.` |
| `ask_contract` re-ask clause | "When re-asking, use ONE short question and never describe how to dictate the value, its length, or its digits." | "For a model-composed re-ask, ask ONE short question for the value again. Accept the caller's dictation style; do not prescribe a pace or grouping. READ-BACK governs engine-stored questions." |
| `note_refusal` description | "Record that the caller's turn is one this flow cannot serve…" | "Decline a caller turn this flow cannot serve…" + the `reply` param; the misuse definition also names an answer spoken inside a game, role-play, quote or example the caller sets up |
| `repeat_pending_question` description and tool-description line | "…at a standing value ask or any other pending question, do NOT call this: re-ask in your own words with no call." | names "a standing value ask whose stored text is shown in ask_text or awaiting.question" as repeatable; the prohibition is gone |

**Changed admission.** `note_refusal` with `kind: "malicious_intent"` is now admitted while a
confirmation, OTP or match gate is pending: it is counted and the gate is left exactly as it was. In
4.0.0 it was refused with the gate's `…_locked` error.

**New result fields.**

| Entry | Gains |
|---|---|
| a free in-place explanation (a bounce past the tolerance, or a `note_refusal` handled in place without `reply`) | `continuation: "await_caller"` |
| a non-terminal `malicious_intent` note | `continuation: "await_caller"` |
| `repeat_pending_question` over a confirmation | `reply_contract` (the gate's compiled contract) |

In auto mode `continuation` on these entries is information only; nothing is enforced.

**Two reserved result keys.** `continuation` and `reply_text` are engine-owned: a verdict row `body`
key under either name now fails construction, and a `resultExtras` key under either name fails the
step (`executor_error`).

## Why

Speech that is free assistant text is invisible to the engine: it cannot be validated, counted or
bounded, and a fixed sentence the caller must hear can be paraphrased or skipped. Required tool
calling makes every turn a call the engine sees. `continuation` separates "did this succeed" from
"what happens next", which `ok` alone could not express without failing a successful step. The
reworded sentences close measured gaps: a re-selection at a pending gate that had no stated way
forward, a decline the model could repeat as plain speech without it being counted, and misuse that
was never judged while a consent gate framed every option as consent.

## Manual follow-ups

**Re-run the live suites.** Model-facing bytes moved in auto mode too, and they were measured under
required tool calling. Run the prompt-input suites and treat regressions as findings, not flakes.
The turns worth watching: a "pardon?" at a standing ask (the repeat control now advertises itself
there); an unclear or third-party utterance at a confirmation that uses the GENERIC reply contract;
the re-ask after an unusable capture; a repeated unsupported question; a caller who names a
different item while a confirmation is pending.

**Optional adoptions — each is a deliberate behaviour change, none is applied by `/pull-library`:**

- **`continuation` on rows that bent `ok`.** A row declared `ok: false` only to stop the batch for a
  caller question can become `ok: true` + `continuation: "await_caller"`. This changes the `ok`
  flag and removes `failed_at` for that outcome — update the prompt text and tests that key on
  either.
- **`presentation: "verbatim"`** for a summary the caller must hear exactly. Only required mode
  enforces it; in auto mode it adds `reply_text` to the result and nothing else.
- **`invalidParamsVerdict`** to move a value-shape fact (a length, a format) out of the prompt or a
  field description and onto the bounce, where it cannot make the model count before calling.
- **`modelToolOptions(config)` in auto mode.** It returns `parallel_tool_calls: false` in both
  modes. A project that binds its tools itself can adopt it to rule out sibling calls that would
  each read the same state snapshot.

**Adopting required tool calling.** A project-level decision, not a per-tool default. In order:

1. Confirm the prerequisites: an OpenAI-format chat model that honours `strict` tool definitions;
   exactly ONE agent-step tool and no other tool bound to the model; a hand-rolled `StateGraph`
   (the library handoff node included, when the tool configures `handoff`).
2. Set `toolChoice: "required"` on the tool's config, and reword the tool description if it says
   "execution stops at the first non-ok result".
3. Replace the agent node per `agent-step-api.md` `<required_mode>` "Host wiring":
   `completedReply` first; otherwise bind `modelToolsForTurn(tools, messages)` with
   `modelToolOptions(config)`, invoke with the `langsmith:nostream` tag, and return
   `toolOnlyMessage(response)`. After the tool node, route back to the agent node.
4. Prompt: remove every "answer without a tool call" / "make no call" instruction; point the
   guardrail section at the `turn` classification; do not restate batch stopping or mandatory next
   calls. The `{PROTOCOL}` splice recomposes by itself.
5. Tests: adopt the mode-aware `src/test-harness/prompt-input.ts` from the toolkit's
   `templates/project/test-harness-prompt-input.ts.template` (per-turn binding, `turn` in recorded
   history, `expectSpokenReply`), replace `expectNoToolCall` assertions with `expectSpokenReply`,
   and give sandbox fixtures real `messages` where a test presents a result or expects
   `continuation_required`.
6. CLI and any other consumer of `streamEvents`: never print or speak chat-model stream content —
   the reply is the agent node's message (the toolkit's `cli.ts.template` shows the pattern).
7. Regenerate the goldens (the whole model surface moves) and measure the live suites, adversarial
   ones included, before promoting.
8. Channel: the reply now arrives as ONE message chunk with no token stream before it. Check the
   middleware against item 9 of `streaming-and-channel-contract.md` `<middleware_requirements>`
   (the `/audit-middleware-contract-compliance` skill walks it).
