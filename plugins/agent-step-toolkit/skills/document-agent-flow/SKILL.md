---
name: document-agent-flow
description: Documents any agent-step agent as a three-part set built from ONE data source — a Markdown design document, a self-contained interactive graph (stage bands, one box per step, ⚡ trigger chips on the edges, happy/branch/failure/optional edge styles, click-for-detail panel, sheet tabs, light/dark, phone width) and an xlsx step sheet (Steps, Triggers & APIs, optional domain sheets, Open & TBD). Works from a prose description, an existing agent-step codebase, or a set of documents (specs, user stories, an owner's walkthrough); all three end in the same validated flow spec, auto-laid-out graph and verification script. Use when someone wants the step ladder of an agent written down, reviewed, re-planned onto agent-step, or kept in sync with its code.

<essential_principles>
This skill produces documentation, never agent code. The deliverable is `<slug>.md`, `<slug>.html` and `<slug>.xlsx`, generated by the vendored `flowdoc` builder from one flow spec. Adopt these rules across every workflow:

**1. One data source; never hand-edit an output.** The spec (`references/data-model.md`) feeds the graph, the sheet AND the Markdown. A correction goes into the spec, then everything rebuilds. The first attempt this skill is distilled from kept three hand-maintained files; within a day the graph contradicted the prose (a trigger moved to an earlier step with no marker). The single-source generator exists because of that drift.

**2. The flow comes from its owner, verbatim.** When a walkthrough exists, it is the source of truth for the ladder — its steps, their order, what each gathers. Specs and code are consulted for fields, documents and real routes, never to reshape the flow. A spec's silence is not a ruling: a field the spec omits but the owner wants is in. Your own suggestions are labelled as suggestions and parked as open items.

**3. Fix the vocabulary before drawing anything.**
- A **step** gathers until a completeness check passes; every turn it acknowledges what it got and lists what is pending.
- A **trigger** is a plain API call fired when a step closes. Several run in order; the first failure decides where the flow goes.
- Human input between two backend calls forces a new step. Consecutive calls with nothing gathered between them stay one step's trigger chain, run by that step's single closing action (a model-built batch only stops on a ✗ verdict row, so a business conflict returned as success would sail through).

**4. Every route or code claim carries `file:line` evidence, or is TBD.** The validator refuses a trigger marked `exists`/`change` without `evidence`. Read the method body, not its name — in the reference project an "OCR this upload" flag turned out to OCR a single document type.

**5. One search finding nothing is not proof of absence.** Three "does not exist" claims in the reference project were wrong, each from a single grep: one repo, one literal token blind to a shared constant or an object spread, one file instead of the controllers. Before writing "does not exist", search a second way that fails differently (name variants, constants, spreads, client interfaces, API specs, settings, sibling repos), then write the scoped claim: "not found on <surface>, searched <how>".

**6. Every open item carries a default.** Work never blocks on a question. Each item is phrased in plain words, with its options and their trade-offs, and the default used until the owner rules.

**7. Every step and trigger carries a status:** `exists` (built, reachable today) · `change` (built, needs a change for this ladder) · `new` (nothing today) · `tbd` (unverified). The status dot, pill and fill are driven by it everywhere.

**8. The engine column speaks current agent-step.** Express each step with the library's own primitives (verdict rows, gates, flows, asks, ladders, handoff routes — `references/engine-notation.md`), read from `../create-tool/references/agent-step-api.md`, not from an older vendored copy in the project under study. The validator refuses primitives the library has removed (`ExecutorResult`, bounded choices, `guardTurn`, `deflect_aside`, `ttlMs`…) and the non-library `readOnly` flag.

**9. Verify in each output's own medium, and report what you observed.** `verify.py` rebuilds twice (determinism), reads the xlsx back, checks the md sections, renders the page headless in light, dark and 400 px (0 console errors, no horizontal scroll, every step opens its own panel, no label or chip over anything as rendered), checks that no edge passes through a box and every ⚡ chip sits on its own edge, and break-tests the validator (eight ways) and the page. A skipped check is printed in the final line — "ALL CHECKS PASSED (1 SKIPPED …)" is not a pass for that check. "Built" is not "verified"; name the check and its result.

**10. Adversarial review before the owner sees it.** A fresh reviewer agent with the `references/research-briefs.md` §Review brief spot-checks claims against source. On the reference it caught three real errors: a capability refuted by the source, stale text that contradicted a later correction, and a step that broke the document's own "one closing action per step" rule.

**11. Public-safe by default.** Outputs describe someone's system. Never paste customer data, credentials or live probe output into a spec. When the set is bound for a public place, run `verify.py --deny <file>` — a file of regexes, one per line, matched case-insensitively against the text of the outputs (the page's data strings, not its coordinates or markup) and every `.py/.json/.md/.txt` beside the spec.
</essential_principles>

<quick_reference>
**Install the generator into the project once** (vendored like the agent-step library, so teammates can rebuild without the plugin):
```bash
cp -r <this skill>/templates/flowdoc scripts/flowdoc          # never edit; re-copy to upgrade — `diff -r` the two
mkdir -p docs/<slug>/source && cp <this skill>/templates/flow_spec.py.template docs/<slug>/source/<slug_>_flow.py
# <slug_> = the slug with "-" → "_", so sibling modules and linters can import it
```

**Build and verify:**
```bash
uvx --with openpyxl python3 scripts/flowdoc/build.py docs/<slug>/source/<slug_>_flow.py --out docs/<slug>
uvx --with openpyxl --with playwright python3 scripts/flowdoc/verify.py docs/<slug>/source/<slug_>_flow.py \
    --out docs/<slug> --shots <scratch>/shots [--deny forbidden.txt]
uvx playwright install chromium     # once per machine, if verify reports no browser
```

**Spec skeleton** (full schema: `references/data-model.md`):
```python
FLOW = {
  "meta": {"slug": "...", "title": "...", "subtitle": "...",
           "engine_version": "3.0.1",          # the toolkit's templates/agent-step/VERSION — shown top-right
           "code_engine_version": "1.4.0"},    # optional: the project's src/agent-step/VERSION
  "stages": [{"id": "A", "name": "Start"}, ...],
  "steps": {"S0": {"stage": "A", "title": "...", "completion": "...", "next": [{"to": "S1", "when": "..."}],
                   "engine": "...", "status": "exists", "triggers": ["T1"], "required": [...]}, ...},
  "triggers": {"T1": {"name": "...", "short": "...", "real": "...", "evidence": "file:line", "on_ok": "...", "status": "exists"}},
  "terminals": {"END": {"label": "Done"}},
  "open": [{"id": "Q1", "question": "...", "where": "S3", "default": "..."}],
}
```
Outcome kinds: `main` (default) · `branch` · `fail` · `opt`. A step with `parent` sits inside that step's container box; `cross_cutting: true` makes it a full-width bar.

**No coordinates anywhere.** The layout is automatic (`references/layout.md`): spine in lane 0, branch lanes to the right, back edges in gutters, self-loops, containers.
</quick_reference>
