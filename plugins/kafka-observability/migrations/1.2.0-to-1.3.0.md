# observability library 1.2.0 → 1.3.0

Event-volume release: **opt-in run filtering** over `run_type:name` glob patterns
(`KAFKA_RUN_FILTER_MODE` = `off` | `allow` | `deny`, default `off`;
`KAFKA_RUN_FILTER_PATTERNS` = comma-separated globs, where the name side matches the run
name OR `metadata.langgraph_node`). Motivated by payload verification in
ib-password-reset-agent-ts: ~73% of a real turn's events (the `__start__` pseudo-node,
auto-generated conditional-edge `RunnableLambda` wrappers, and thin `agent`/`tools`
wrapper nodes) were byte-duplicates of content already carried by the root, llm, and tool
events. The root run always survives filtering, in both modes — it carries the full
invocation input/final state and is the only event without `metadata.langgraph_node`
(the turn-boundary marker for timeline consumers).

Additive only: event schema, transport, wiring (`startup()` once at graph entry), and the
disabled-by-default contract are identical to 1.2.0. **With filtering off — the default —
emitted bytes are identical to 1.2.0**; no consumer's data changes shape without opting
in. Inconsistent filter config (invalid mode, mode without patterns, patterns without a
mode) throws at startup — no-config-fallback rule.

<transforms>

**1. `.env.example` — document the new optional filter vars.**
Append to the existing Kafka observability block (immediately after the
`KAFKA_ATTACH_MODE` lines):

```
# Opt-in run filtering: off | allow | deny (default off = every run emitted; see src/observability/README.md "Run filtering")
# KAFKA_RUN_FILTER_MODE=off
# KAFKA_RUN_FILTER_PATTERNS=
```

check: `grep -q "KAFKA_RUN_FILTER_MODE" .env.example` — if it already matches, skip
(idempotent). Deployment settings files need **no** change: the default (`off`) preserves
current behavior everywhere; enabling filtering in an environment is a deliberate,
per-app decision (see advisory below).

**2. Advisory (not a transform): opting in safely.** Filtering is only lossless for runs
whose payloads are verified duplicates in THIS app:

- `chain:__*` (framework pseudo-nodes) is safe by construction in any LangGraph app —
  `__start__` never transforms state.
- Named wrapper nodes (`agent`, `tools`, routing `RunnableLambda`s) are droppable ONLY
  after field-by-field comparison against real payloads shows they delegate to exactly
  one nested run and return its output verbatim. A cross-repo survey found nodes that
  merge/strip the nested run's output and nodes with no nested run at all (KB-driven
  envelope builders, escalation writers, untraced I/O in the node body) — those must
  never be filtered. Re-verify when node code changes.
- Before enabling in a shared environment, confirm downstream consumers do not walk
  `parent_run_id`/`dotted_order` chains: filtering never re-parents, so surviving events
  may reference dropped runs.
- A verified allowlist example (ib-password-reset-agent-ts):
  `KAFKA_RUN_FILTER_MODE=allow`,
  `KAFKA_RUN_FILTER_PATTERNS=llm:*,tool:*,chain:resolve_handoff`.

**3. Advisory (not a transform): log tooling.** When a filter is active, startup logs
`[observability] run filter active: mode=… patterns=… (root run always emitted)` — worth
capturing in dashboards so an environment's event volume is explainable from its logs.

</transforms>
